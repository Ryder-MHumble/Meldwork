# Meldwork 市场与用户调研说明书

> 版本：OPC 开源优先版
>
> 日期：2026-07-31
>
> 状态：战略工作稿；外部价格、竞品能力和法律结论在公开发布前需要刷新

## 0. 结论先行

### 0.1 值不值得做

**值得继续做，但当前最合理的目标不是立即做成一个 SaaS，而是做成一个有真实用户价值的开源 Agent Harness 项目。**

Meldwork 已经完成了有价值的 0-1 基础：本地 Electron 工作空间、已支持 Agent CLI 的发现与调用、直接和群组会话、兼容条件下的原生 Session 延续、有限轮次的自动讨论、Skill 与图片上下文、Provider 配置、安全存储和较窄的 Renderer/Main 边界。这些能力足够支持公开 MVP 和真实用户验证，但还不足以证明它是一个独立商业品类。

真正值得继续投入的命题不是“把更多 Agent 放在一个窗口”，而是：

> **当一项工作需要多个 Agent 或需要一个可控的 Agent 执行环境时，Meldwork 能否让任务更容易交接、更容易复核、更容易复用，并且不迫使用户迁移已有 Agent 账户和工作方式？**

这个命题与用户目前的 OPC 资源更匹配：先用开源和内容建立分发，再用真实使用数据决定是否做 Harness 产品、团队治理或商业支持。

### 0.2 为什么不是“多智能体聊天器”

单纯聚合本地 CLI 的功能很容易被上游 Agent、IDE、终端和云端控制面吸收。多 Agent 的数量、头像、群聊和自动轮次都不是长期壁垒；用户愿意留下来的理由必须是：

1. **连接保真**：保留各 Agent 的原生会话、权限和 Provider 关系。
2. **工作保真**：任务、运行、交付物和复核记录不会被聊天消息淹没。
3. **控制保真**：用户知道哪些数据出站、哪个 Agent 可以写入、什么时候必须人工确认。
4. **结果可比**：可以比较独立尝试、审查意见、测试结果和成本，而不是只看谁的文案更流畅。
5. **开放扩展**：本地、云端、自定义和渠道型 Agent 都通过统一 Connector 加入，避免被单一厂商锁定。

### 0.3 OPC 的决策

在一个人、且有日常工作的前提下，项目不能同时追求以下全部目标：广泛适配、企业销售、云端基础设施、完整团队协作、持续内容运营和高频版本迭代。

因此采用三层目标：

| 层次 | 目标 | 现在是否投入 |
| --- | --- | --- |
| 项目目标 | GitHub 上可安装、可理解、可演示的开源 MVP | 立即投入 |
| 产品目标 | 验证“跨 Agent 工作连续性 + Harness 控制层”是否产生重复价值 | 立即投入，但只做一个主场景 |
| 商业目标 | 为 Connector 兼容、治理、支持和私有部署保留收入选项 | 有付费信号后再投入 |

### 0.4 直接判断

- **做成高质量开源项目：值得。** 它能带来用户、贡献者、行业声誉和职业资产，即使后续没有商业化也成立。
- **直接做通用企业平台：不值得。** OPC 无法承受长期兼容、销售、支持、安全与合规的固定成本。
- **探索 Harness 商业化：值得保留。** 但必须先由开源项目验证一个重复、昂贵、可标准化的问题。
- **继续堆 Agent 适配器：不值得作为主线。** 适配器数量只有在兼容性、任务结果和社区贡献形成闭环时才有价值。

## 1. 研究边界与证据口径

### 1.1 已有证据

- 当前仓库代码、测试和架构文档对 MVP 能力的审计。
- 既有市场研究中的公开调查、竞品官方文档与价格快照。
- 对本地 Agent、Cloud Agent、控制面和工作渠道的产品趋势判断。

### 1.2 尚未有的证据

当前没有足够的外部证据证明：用户会为跨厂商中立工作层单独付费；多 Agent 的质量提升能稳定覆盖额外时间和 Token 成本；团队需要一个新的控制面；或者开放 Connector 会自动形成网络效应。

因此本文将结论分为：

- **事实**：仓库或公开来源可以直接支持。
- **推断**：由事实推导出的战略判断。
- **假设**：需要访谈、真实任务、留存或回款验证。
- **决策**：在 OPC 约束下采取的取舍。

### 1.3 对外使用规则

外部材料不得把“将来可连接任意 Agent”“Cloud Agent”“审计治理”“企业级安全”写成当前已交付能力。当前 MVP 仍是固定适配的本地 Agent 工作空间；“Harness 基座”是产品方向和设计目标。

## 2. 市场正在发生什么

### 2.1 Agent 已从聊天入口变成执行入口

Coding Agent、研究 Agent、终端 Agent 和企业自动化 Agent 都在向文件访问、工具调用、长任务、后台运行和多渠道交接发展。用户不再只面对一个问答框，而是面对多个可执行系统。

这带来两个变化：

1. Agent 本身越来越像基础设施，单个 Agent 的差异会被模型、工具和生态持续重写。
2. 用户真正缺少的是工作状态、权限、运行结果、证据和验收的统一管理。

### 2.2 多 Agent 是机会也是陷阱

多 Agent 只有在以下条件至少满足一个时才有价值：

- 任务风险高，第二个独立视角能降低漏检概率。
- 任务复杂，单个 Agent 的上下文或工具覆盖不足。
- 工作需要不同专业角色，且交付格式可以比较。
- 用户本来就拥有多个 Agent，手工切换成本稳定存在。

否则，多 Agent 只会增加 Token、等待时间、输出合并和责任归属问题。

### 2.3 用户信任比 Agent 数量更稀缺

公开调查和行业研究反复显示，开发者采用 AI 的速度很快，但对准确性、隐私和结果可控性的信任并没有同步增加。历史研究还提醒我们：主观“更快”不等于真实交付更快。

对 Meldwork 的含义是：产品指标不能只统计运行次数、消息数或 Agent 数量；必须记录任务是否完成、结果是否被采用、发现是否被修复、成本是否合理，以及用户是否再次使用。

## 3. 市场分层与竞争格局

### 3.1 价值链

| 层级 | 用户购买的结果 | 代表性方向 | Meldwork 的位置 |
| --- | --- | --- | --- |
| Agent / 模型 | 生成、推理、执行能力 | Codex、Claude Code、Kimi、Qwen 等 | 连接供给，不与之竞争 |
| IDE / Terminal | 在当前开发环境里完成任务 | Cursor、Cline、Warp 等 | 不复制完整 IDE |
| Cloud Agent | 离线运行、后台执行、PR 交付 | GitHub、Cursor、Devin、Factory 等 | 未来 Connector |
| Agent Control Plane | 并行调度、策略、审计、状态 | Agent HQ、Warp Oz、OpenHands 等 | 未来竞争与合作层 |
| Work Channel | 在 GitHub、Slack、Linear、飞书等地派发工作 | Issue、PR、消息渠道 | 未来 Channel |

### 3.2 直接与相邻竞品

| 竞品/方向 | 强项 | 对 Meldwork 的威胁 | 不应正面复制的部分 |
| --- | --- | --- | --- |
| GitHub Agent HQ / Copilot | 代码托管、PR、组织治理、渠道分发 | 能把多 Agent 变成平台标配 | GitHub 全栈控制面 |
| Cursor / Cline / Warp | 强入口、IDE/终端体验、并行任务 | 用户不需要额外工作台 | 完整 IDE 或终端替代 |
| OpenHands | 开放、自托管、Runtime 和第三方 Agent | 与中立 Harness 叙事接近 | 大规模 Runtime 与云基础设施 |
| Devin / Factory | 以交付结果、企业合同和云执行为中心 | 在高预算企业中直接卖结果 | 企业销售和云执行舰队 |
| 各家 Agent 原生 Teams | 对自家模型、工具和账号优化 | 用户可留在单一生态 | 单厂商闭环 |

### 3.3 竞争空位是假设，不是事实

Meldwork 的切入假设是：有一批用户已经同时使用多个 Agent，愿意保留本地控制，却缺少一个跨厂商的工作和证据层。这个假设只有在以下三项同时成立时才有意义：

1. 手工协调每周重复发生，且耗时足以让用户抱怨。
2. 跨 Agent 的独立尝试或审查能改善结果，而不只是增加成本。
3. 用户愿意把这层工作状态交给一个开放项目，或愿意为兼容与治理服务付费。

## 4. 目标用户与真实 Jobs to Be Done

### 4.1 第一用户群：多 Agent 重度个人用户

**特征假设**：已使用两个或以上 Agent；能理解 CLI、工作目录和权限；在复杂编码、研究、规划或审查任务中主动切换工具。

**核心 Job**：

> 当一项工作重要到不能只相信一个 Agent 时，我希望让不同 Agent 在不丢失原生会话和上下文的情况下参与同一个任务，并快速判断哪些结果值得采用。

**为什么先服务他们**：访谈成本低、安装决策短、开源传播意愿高、可以直接提供真实任务；他们不需要先购买组织级治理。

### 4.2 第二用户群：小型 AI-native 团队

**核心 Job**：

> 当团队成员使用不同 Agent 时，我希望有一套共享的任务、权限、验证和交付规则，而不是依赖每个人手工维护 CLI 习惯。

**进入条件**：必须先证明个人用户重复使用，再验证团队是否真的需要共享策略、审计和预算；不能因为“企业愿意听演示”就提前做团队平台。

### 4.3 未来高价值用户：高责任工作团队

研究、咨询、安全、架构评审和重大迁移等场景对 Evidence 和 Acceptance 的需求更强，但错误成本、合规和支持成本也更高。它们只能作为设计伙伴与未来商业化方向，当前不得宣传为生产级能力。

### 4.4 暂不优先

- 只用一个 Agent 做简单任务的用户。
- 只追求最低 Token 价格的用户。
- 期待无人值守“自动赚钱”的泛自动化用户。
- 需要完整 IDE、云执行和企业 SSO 的用户。
- 不能接受本地 Agent 仍可能访问外部 Provider 的用户。

## 5. 痛点优先级

| 优先级 | 痛点 | 频率假设 | 用户损失 | 产品机会 |
| --- | --- | --- | --- | --- |
| P0 | 上下文、Session 和结果散落在不同 Agent | 高 | 重复解释、丢失决策 | 持久工作空间与 Session Fidelity |
| P0 | 不知道该信任哪个输出 | 中高 | 错误进入交付 | 独立尝试、审查、Evidence 和验收 |
| P0 | Agent 权限和 Provider 出站不透明 | 中 | 安全事件、误写入 | 本地控制面、能力与出站声明 |
| P1 | 多个结果难以合并成可复用交付物 | 中高 | 手工整理 | Artifact、差异、导出与复验 |
| P1 | Agent 版本变化导致适配失效 | 中高 | 维护成本和不稳定 | 兼容矩阵、Contract Test、社区适配 |
| P2 | 本地与 Cloud Agent 不能连续交接 | 增长中 | 任务中断 | Local/Cloud Handoff |
| P2 | 团队不能统一策略、预算和审计 | 中 | 影子 AI 与采购风险 | Team Policy、成本和审计 |

## 6. 核心竞争力：从聚合工具到 Harness 基座

### 6.1 Connector Contract

每个 Agent 不只提供一个启动命令，还要声明：能力、输入限制、Session 生命周期、权限模式、事件流、Artifact/Evidence 回传、成本时延和数据出站边界。

### 6.2 Task → Run → Artifact → Evidence → Acceptance

这是产品数据模型和用户叙事的共同骨架：

1. **Task**：要解决什么问题、验收标准是什么。
2. **Run**：由哪个 Agent、哪个版本、什么权限和 Provider 执行。
3. **Artifact**：代码变更、文档、结论、文件或链接。
4. **Evidence**：测试、来源、日志、差异、审查发现。
5. **Acceptance**：人类接受、拒绝、修改、Apply、Commit、Export 或 Reopen。

### 6.3 Compatibility Intelligence

真正的生态资产不是“支持过多少 Agent”，而是：哪些 Connector 在什么版本、系统和任务类型上可靠；失败发生在哪里；哪些能力可以安全组合。公开兼容矩阵、Contract Test 和失败复现，比一张超长 Agent Logo 墙更有价值。

### 6.4 Local Control Plane

控制面和工作记录默认保留在本机，但不能宣传成“所有数据永不出网”。用户必须看见：Provider、模型、权限、工作目录、图片/Skill 是否出站，以及 Cloud/Channel 连接何时获得授权。

### 6.5 Open Ecosystem

连接器、能力清单、评测任务和文档要尽可能可贡献；核心客户端保持清晰的安全边界。开源项目的网络效应来自：更多真实适配、更多兼容数据、更多任务模板和更低的新用户安装成本，而不是单纯的 Star 数。

## 7. 开源优先的增长判断

### 7.1 为什么开源是 OPC 的最优起点

- 降低信任门槛：用户可以检查本地数据、权限和执行边界。
- 降低获客成本：GitHub、视频和社区内容可以长期累积。
- 允许生态共建：适配器和评测任务不必全部由一个人维护。
- 即使商业化失败，也保留技术作品、行业影响力和职业资产。
- 可以先用真实使用数据判断是否存在独立付费价值。

### 7.2 开源不能自动解决的问题

- 许可证、依赖和商标边界仍需要明确。
- 用户安装、升级、签名、兼容和支持仍然需要维护。
- Star 不等于安装，安装不等于重复使用，重复使用不等于付费。
- 过早支持太多 Agent 会把 OPC 变成免费的兼容性客服。

### 7.3 90 天可观测指标

**北极星指标：** 每周完成至少一个“跨 Agent 可复核工作闭环”的活跃 Workspace 数量。

辅助指标：

- GitHub：Star、Fork、Issue 质量、外部 PR、文档点击。
- 产品：安装成功率、首次任务完成率、第二周回访率、跨 Agent 任务占比。
- 价值：被用户接受/导出的 Artifact 数、被复验的 Evidence 数、重复任务数。
- 社区：有效反馈人数、贡献 Connector 数、内容带来的安装数。
- 商业信号：愿意参与设计伙伴、愿意付支持费、愿意试用团队策略的用户数。

Star、曝光和候补名单不能替代激活、重复使用和真实交付。

## 8. 商业化选项，而非当前承诺

### 8.1 可能的收入阶梯

| 阶段 | 收入方式 | 触发条件 |
| --- | --- | --- |
| 开源期 | 免费核心；可选赞助、咨询和培训 | 先建立信任，不把赞助当产品收入 |
| 早期服务 | 兼容性诊断、部署支持、工作流设计 | 有重复问题且可以标准化交付 |
| Open Core | 团队策略、审计、兼容 SLA、签名 Registry、离线更新 | 个人用户重复使用且团队问题真实存在 |
| Harness 产品 | 私有部署、Channel、Cloud Handoff、预算与策略 | 有 3 个以上相似付费客户和可复用交付 |

### 8.2 暂不锁定价格

当前不直接承诺 `$12-15/月`、按席位或企业年费，因为用户是否愿意在已有 Agent 费用之外购买“中立工作层”尚未被验证。未来可测试：

- 个人 Pro：按高级工作流、导出、模板和兼容便利收费。
- 团队：按策略、审计、共享模板和支持收费，而不是按 Token 加价。
- 企业：按私有部署、签名适配、SLA、集成和合规支持收费。

Meldwork 不应代收或加价模型 Token，除非未来明确提供独立的托管执行服务。

## 9. OPC 可承受的验证计划

### 第 1 阶段：公开 MVP（0-6 周）

- 统一 README、安装路径、截图、演示视频和问题模板。
- 只承诺当前已验证的本地 Agent 和 macOS 体验。
- 把 Task/Run 的最小结构先落在本地数据中，不建设云服务。
- 找到 10-15 名愿意完成真实任务的早期用户。

### 第 2 阶段：价值实验（7-12 周）

- 只做一个主场景：实施 Agent + 独立审查 Agent。
- 记录用户手工切换耗时、结果质量、误报、成本、等待和最终采用情况。
- 观察同一用户是否在 30 天内重复使用，而不是只看首日反馈。
- 让用户直接提出第一个 Connector、模板和 Evidence 需求。

### 第 3 阶段：决定方向（12 周后）

- 若个人用户重复使用明显：继续开源产品和生态。
- 若团队治理需求重复出现：做 1 个标准化付费试点，不做完整企业平台。
- 若价值仅来自统一窗口：收缩为稳定的个人开源工具。
- 若多 Agent 质量收益不稳定：把重点转到 Harness 基础设施、单 Agent 质量和可验收工作流。

## 10. 主要质疑与回应

### “这只是 Wrapper。”

MVP 阶段这个质疑部分成立。只有 Connector Contract、Session Fidelity、Evidence、Acceptance、兼容矩阵和安全边界形成闭环后，才有资格称为 Harness 层。

### “上游 Agent 会自己做。”

这是最高风险，也是坚持跨厂商中立的理由。Meldwork 不争模型、IDE 或云算力，而是服务用户已经购买和配置的不同 Agent。

### “大部分任务一个 Agent 就够了。”

成立。产品必须默认单 Agent，只有高风险、低确定性或需要独立审查的任务才建议多 Agent。

### “开源以后怎么赚钱？”

先不把赚钱当作成立条件。未来可以通过兼容、治理、支持、私有部署和 Cloud/Channel 集成收费；是否成立由真实回款决定。

### “本地优先是不是完全离线？”

不是。Meldwork 的工作记录和控制面可以在本机，但被选中的 Agent 和 Provider 仍可能访问网络。

## 11. 最终判断

Meldwork 的开源机会来自“把 Agent 作为可替换执行单元，把工作作为可持续、可验证的对象”。

OPC 阶段最重要的不是把路线图写得更大，而是让每一个用户能在几分钟内理解、安装、完成一次真实任务，并愿意回来再做一次。如果这个循环成立，商业化是可选的放大器；如果不成立，及时收缩为高质量开源工具仍然是成功结果。
