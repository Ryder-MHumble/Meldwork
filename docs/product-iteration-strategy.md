# RoundRelay 产品评审与迭代战略（内部版）

> 状态：战略草案，供两院内部决策与工程排期使用
>
> 产品名：RoundRelay
>
> 中文工作名：**群智接力**
>
> 证据基线：2026-07-30 的仓库与工作区快照
>
> 适用阶段：内部 Alpha 到两院封闭试点
>
> 复审节奏：每 4 周复审一次；当产品边界、数据政策或主目标用户发生变化时立即复审

## 0. 一页结论

### 决策建议

**建议有条件继续投入，暂不进入公开发布。** RoundRelay 已经具备一个可信本地桌面产品的技术骨架：Electron 主进程承担权限边界，本地 Agent 可被发现与调用，首次引导、单聊和群聊、`@` Skill、图片附件与会话引用已经形成实现和自动化验证，工作目录默认只读，自动讨论有轮数、时间和停止上限。这些能力足以支持院内 Alpha，不足以证明“多 Agent 一定比单 Agent 更有效”，也不足以支撑高敏感数据、Windows 正式发布或无人监管的自主辩论。

下一阶段不应继续以“支持更多 Agent、增加更多聊天功能”为主线，而应验证一个更窄的产品命题：

> **RoundRelay（群智接力）是一款面向两院知识工作者的本地优先多智能体协作桌面端：在用户掌控上下文、工作目录权限和模型去向的前提下，将已有异构本地 Agent 组织为可持续对话、分工接力和可审计审校。**

战略重点是从“多个 Agent 在一个聊天框里轮流说话”，升级为“围绕高价值任务形成可验证的工作结果”。若 12 周试点不能证明它相对“直接使用最强单 Agent”在质量、速度或风险发现上至少有一项达到预设门槛且方向稳定的优势，应收缩为统一的本地 Agent 工作台，不继续投入复杂自治编排。

### 战略范围说明

本文评审对象是当前仓库中的 **RoundRelay 本地桌面产品**，不是最初设想的“云 Agent + 本地 Agent + 多个人类同事”完整两院协作平台。两者应按“本地切入点与上层平台”的关系管理，而不是混为同一个已交付产品：

- RoundRelay 先验证本地 Agent 互联、任务接力、权限控制和多 Agent 净收益，是可独立使用的产品，也是未来混合平台可复用的桌面执行节点。
- 原始两院平台若继续推进，负责组织身份、同事协作、云 Agent、任务发布和跨端共享；它不能绕过本地端的数据去向确认与执行授权。
- 在 RoundRelay 尚未证明高价值任务收益、协议稳定性和安全边界前，不把云端群聊、多用户实时协作或跨设备同步纳入当前路线图。
- 后续若立项混合平台，应单独定义身份、消息同步、权限继承、云本地路由和审计架构，不以“给 RoundRelay 加一个服务器”代替战略与安全评审。

### 当前阶段判断

| 维度 | 判断 | 说明 |
| --- | --- | --- |
| 技术可行性 | 中高 | 本地执行、IPC 边界、持久化、首次引导、Skill/图片上下文、适配器和有界自动讨论已有代码与测试证据 |
| 发布成熟度 | 中低 | macOS 仅适合内部验证；未完成正式签名、公证、自动升级和完整真机矩阵 |
| 用户价值证据 | 低 | 仓库内没有访谈、行为数据、任务效果对照或留存证据 |
| 差异化潜力 | 中高 | “本地控制 + 异构 Agent + 结构化审校”组合有价值，但仅支持多个 CLI 很容易被复制 |
| 安全可信度 | 中 | Electron 边界和密钥存储较强，但 Agent 仍以本机用户权限运行，聊天数据未做应用层加密，安装源未锁定摘要 |
| 自主辩论成熟度 | 低 | 当前是顺序轮询、提示词约束和一致同意标记，不是角色化、证据化、可评测的辩论协议 |

### 投资条件

未来 12 周只在以下条件下继续加码：

1. 找到至少 2 个高频且高价值的院内任务，用户愿意每周重复使用。
2. 对照最强单 Agent，RoundRelay 在盲评质量、风险发现或总用时上至少一项达到 20% 的方向性提升门槛，且没有明显增加返工；正式扩大前必须同时报告样本量、评审一致性和区间估计。
3. 真实 Agent 调用失败率、写入越权、敏感信息外发和安装供应链风险达到本文件定义的发布门槛。
4. 用户能正确理解“本地优先不等于完全离线”，不会把第三方 Provider 出网误认为 RoundRelay 云端上传。

### 明确不做

- 不做新的院内即时通信工具，不替代钉钉或现有协作平台。
- 不做远程多人群聊、云端频道和云端会话存储。
- 不把“无人值守自治”作为近期卖点；任何多轮运行都必须可见、可停、有预算、有责任人。
- 不以支持 Agent 数量作为核心成功指标。
- 不承诺 RoundRelay 能提供操作系统级沙箱；上游 CLI 的权限标志必须经过真机验证。
- 不在缺少效果对照前建设复杂的 Agent 市场、公共社区或跨设备同步。

### 目标版本内部发布稿

> RoundRelay 面向两院首批试点人员开放内部版本。研究员、工程师和产品人员可以在自己的电脑上，把已经安装的 Codex、Hermes、WorkBuddy、OpenCode 等 Agent 放进同一任务工作台，明确选择工作目录、读写权限和模型去向，让不同 Agent 分别提出方案、审查风险、补充证据并由用户确认最终结果。RoundRelay 不建立云端会话服务，也不替代现有多人协作工具；会话与编排状态保存在本机，但所选 Agent 或模型 Provider 仍可能访问网络，产品会在运行前清楚显示数据去向和权限范围。

### 名称与视觉系统

- **产品名：RoundRelay。** `Round` 同时指多轮讨论、不同视角和围绕同一任务的回合；`Relay` 指上下文、方案、证据和产物在异构 Agent 之间接力。名称直接表达“轮次讨论 + 能力接力”，比泛化的 Agent Hub、Agent Chat 更能承载产品差异。
- **中文工作名：群智接力。** 适合两院内部沟通，强调集体审校和结果传递，不暗示无人自治。是否作为正式对外中文名，应在试点前由品牌负责人确认。
- **Logo：3D Relay Fold。** 三段折叠箭带形成持续循环，分别表达提出、质询和收敛，也可理解为多个 Agent 围绕同一任务交换主导权。薄荷青玻璃金属与深石墨底提供未来软件感，明确避开齿轮、线路板和工业机械意象。
- **资产规范。** `roundrelay-app.png` 使用透明画布的 3D 应用图标，`roundrelay-favicon.png` 是 64px 小尺寸版本，`roundrelay.png` 保留为深色背景上的产品主标；首启三张 GPT Image 2 示意图沿用明亮 3D 视觉。缩小场景可使用同一几何标记的简化表达，但不得改成齿轮、机械臂或复杂网络拓扑。

## 1. 事实基线：现在到底有什么

### 1.1 证据分级

本文采用四级证据，避免把愿景写成现状：

| 级别 | 定义 | 可使用的表述 |
| --- | --- | --- |
| A：代码 + 自动化测试 + 已执行验证 | 有实现、测试，且仓库记录了实际执行结果 | “已实现并验证” |
| B：代码 + 自动化测试 | 有实现和测试，但没有完整真机或生产环境验证 | “已实现，待真机验证” |
| C：工作区开发中 | 代码处于未提交或未闭环状态，关键调用链缺失 | “开发中，不可视为已交付” |
| D：规划或假设 | 没有实现证据，或只有产品意图 | “计划、假设、待验证” |

### 1.2 能力盘点

| 能力 | 状态 | 证据与边界 | 产品判断 |
| --- | --- | --- | --- |
| 本地优先 Electron 桌面端 | A | `README.md`、`documentation/architecture.md`、`desktop/src/main.cjs`；无账号、应用服务器、远程会话服务 | 是产品底座，应保持，不应为短期便利引入必需云服务 |
| 受限 preload 与主进程 IPC | A | `desktop/src/preload.cjs`、`desktop/src/main.cjs`、主进程安全测试 | 当前最有价值的可信基础之一 |
| 9 类本地 Agent 检测与调用适配 | B | `desktop/src/cli-adapters.cjs`、`desktop/src/agent-installer.cjs` 及单元测试 | 代码支持不等于九类 Agent 在目标设备上都稳定可用；必须以兼容矩阵对外呈现 |

| 固定白名单 Agent 安装 | B | 固定 npm 包或 HTTPS 安装脚本、敏感环境过滤、取消与安装后验证 | 上游包和脚本可变且未校验摘要，是内部扩散前的高优先级风险 |

| 结构化质询、证据核验、反方角色 | D | 当前没有角色、论点、证据、异议和裁决对象模型 | 是下一阶段核心产品能力，不应把现有自动讨论改名冒充 |
| 多个人类实时协作 | 明确不支持 | 架构文档明确只有一个本机人类操作者，无远程参与者或云频道 | 保持边界，通过现有协作工具分享结果 |
| 会话应用层加密、不可篡改审计 | D | 会话 JSON 未做应用层加密；只有本地状态，没有独立审计日志 | 高敏感任务进入试点前需确定制度与技术门槛 |

### 1.3 现有自动讨论的准确描述

当前自动讨论具有真实实现，不应被低估，也不应被包装过度：

1. 用户先发起一个话题，再选择自动讨论轮数。
2. 系统按群组 Agent 顺序逐个调用，每个 Agent 看到同一话题下有限的最近对话。
3. 提示词要求 Agent 在最后输出 `agree` 或 `continue` 标记。
4. 只有所有 Agent 在同一完整轮次成功返回且都标记 `agree`，系统才提前结束。
5. 系统支持失败隔离、后续轮次重试、用户停止、12 轮硬上限和 30 分钟总上限。
6. 带图片的根消息会在启动前检查所有 Agent 能否获得同一组图片；任一目标不支持或数量不足时整轮不启动。Skill 保持目标隔离，不会跨 Agent 传播。

它尚未做到：指定提议者/反方/证据审查者、验证引用来源、判断分歧是否真正解决、比较方案得分、保留少数意见、生成可追踪结论、针对同模型相关性做校正。因此战略上应称为“有界多 Agent 接力讨论”，将“结构化质询与收敛”作为未来目标。

### 1.4 证据缺口

仓库目前没有以下产品证据：

- 至少 5 次目标用户访谈及原始任务样本。
- 真实用户留存、重复任务率、每周任务完成数。
- RoundRelay 与“最强单 Agent”在同一任务上的盲评对照。
- 多 Agent 发现了多少单 Agent 未发现且被人类验证的问题。
- 用户为切换 CLI、复制上下文和合并结果实际花费的时间。
- 高敏感数据是否允许进入第三方 Provider 的院内政策结论。
- 九类 Agent 在目标 macOS/Windows 设备上的完整真机兼容结果。

因此，本文对技术现状的置信度较高，对需求强度和留存的置信度较低。方向判断约 70% 置信度，首要场景排序约 50%，指标目标属于试点假设，不是历史基线。

## 2. 问题定义

### 2.1 核心问题假设

两院内部已经使用多个本地 Agent 的研究员、工程师和产品人员，在高价值任务上面临三类摩擦：

1. **上下文碎片化**：不同 CLI、终端和工具各自保存会话，用户反复复制背景、约束和中间结论。
2. **结果整合成本高**：多个 Agent 可以给出不同答案，但用户仍需手工组织提议、反驳、验证和最终结论。
3. **信任边界不清楚**：用户知道工具“在本机运行”，却未必知道所选 Agent、Provider、安装脚本和工作目录权限具体会把什么数据带到哪里。

这些是待验证问题，不是已证实事实。首轮发现研究必须回答：问题发生频率多高、现有替代方案是什么、什么任务的失败成本足够高，值得承担多 Agent 的额外时间和模型费用。

### 2.2 要交付的用户结果

RoundRelay 的用户结果不是“产生更多消息”，而是：

> 用户用更少的切换和整合成本，得到一个经过独立质询、知道数据去向、能够追溯过程并可以直接继续执行的结果。

### 2.3 三层价值

| 层级 | 用户价值 | 当前成熟度 | 下一步 |
| --- | --- | --- | --- |
| 统一入口 | 首次引导、发现、安装、单聊和继续使用不同本地 Agent | 中 | 做真机兼容与首次成功率，不再增加泛化引导页 |
| 协作接力 | 多 Agent 在同一任务上下文中分工、回应和延续 | 中低 | 从聊天串升级为任务、角色和结果对象 |
| 可信审校 | 有证据的质询、分歧保留、可解释收敛和权限审计 | 低 | 建立结构化协议、评测和安全门槛 |

战略上，统一入口是获客和激活能力，协作接力是使用价值，可信审校才可能形成长期差异化。

## 3. 目标用户与优先场景

### 3.1 首要用户

**首要用户：已经每周使用至少两个本地 Agent CLI、处理非公开代码或文档、需要对重要结果负责的两院知识工作者。**

优先选择这类用户，因为他们已经承担安装、认证和本地环境成本，能立即感知切换与整合摩擦，也更可能评价多 Agent 是否真的增加价值。

| 用户 | 核心任务 | 现有替代 | 成功结果 | 不适合的原因 |
| --- | --- | --- | --- | --- |
| 研发工程师/架构师 | 方案设计、代码审查、故障根因、变更风险 | 多个终端、IDE Agent、人工复制上下文 | 找出关键缺陷并形成可执行修改计划 | 简单补全或机械改动用单 Agent 更快 |
| AI 产品经理/研究运营 | PRD 红队、需求澄清、竞品假设、验收标准 | 单模型聊天、人工评审会 | 更早暴露口径、依赖和失败条件 | 没有原始证据时，多 Agent 只会放大推测 |
| 研究员/技术研究人员 | 研究设计、论证审校、复现实验计划 | 文献工具、单模型问答、同事评审 | 形成带未决问题和证据缺口的审校结果 | 需要在线检索但未配置可信工具时，结论质量不可控 |
| 项目负责人 | 重大方案预演、风险清单、决策备忘录 | 会议、专家咨询、人工汇总 | 缩短准备时间并保留少数意见 | 最终责任不能交给 Agent 共识标记 |

### 3.2 优先任务

| 优先级 | 场景 | 为什么适合多 Agent | 目标产物 | 初始试点建议 |
| --- | --- | --- | --- | --- |
| P0 | 代码/架构变更审查 | 可分为实现理解、反例、测试、安全和整合 | 风险清单、证据位置、修改建议、未决项 | 首批必测 |
| P0 | PRD/方案红队 | 不同角色可独立挑战目标、范围、依赖和验收 | 问题列表、决策建议、修订版验收标准 | 首批必测 |
| P1 | 故障根因与复盘预演 | 多路径假设和反证有价值 | 假设树、验证步骤、置信度 | 有真实脱敏样本后测试 |
| P1 | 研究设计与论证审校 | 需要方法、证据和反方视角 | 证据缺口、偏差风险、复现计划 | 需接入可靠资料后测试 |
| P2 | 长周期自主研究/开发 | 可能受益于多轮迭代 | 可执行成果与完整审计 | 仅在前述任务成立后探索 |

### 3.3 非目标用户与非目标场景

- 只使用一个 Agent、主要做低风险简单问答的用户。
- 需要手机端、多人实时聊天、云端共享频道的团队。
- 希望系统在无人监督下长期运行并直接提交高风险修改的用户。
- 需要 RoundRelay 代管模型账号、统一结算或组织权限的企业客户。
- 把“多 Agent 回复更多”本身当作价值的展示型场景。

## 4. 定位、边界与差异化

### 4.1 类别定位

RoundRelay 不应定位为“AI 群聊软件”，也不应定位为“另一个云端 Agent 编排平台”。更准确的类别是：

> **本地优先的多 Agent 任务审校与接力工作台。**

“聊天”是交互外壳，“任务结果、权限边界和审校过程”才是产品本体。

### 4.2 替代方案比较

| 替代方案 | 擅长什么 | RoundRelay 必须胜出的地方 | RoundRelay 应主动承认的劣势 |
| --- | --- | --- | --- |
| 分别使用各 Agent CLI/终端 | 原生能力完整、用户熟悉、迭代最快 | 减少上下文搬运、统一任务连续性、形成跨 Agent 结果 | 原生 CLI 新功能会先到上游，适配层可能滞后 |
| 单一 IDE/代码 Agent | 深度编辑、工程上下文和操作闭环 | 对重要方案提供独立质询和异构视角 | 日常编码延迟更低，简单任务体验更顺畅 |
| 云端多 Agent 框架/平台 | 集中部署、远程协作、自动化扩展 | 本地状态、用户掌控权限、复用现有 CLI 与认证 | 不提供服务器级调度、组织管理和跨设备协同 |
| 通用聊天/协作工具 | 多人沟通、通知、文件共享、组织关系 | 在本机执行任务并保留 Agent 运行上下文 | 不应复制即时通信能力 |
| 人工专家评审 | 责任清晰、经验深、可处理组织语境 | 降低预审成本，让人工聚焦高价值判断 | 不能取代专家责任和最终审批 |

### 4.3 差异化组合

单个能力都不构成护城河，真正值得投入的是以下组合：

1. **本地控制面**：会话、任务状态、工作目录选择和编排在本机；没有 RoundRelay 云端会话依赖。
2. **异构原生 Agent**：复用用户已经安装、认证和信任的 Agent，而不是把多个相同模型包装成不同角色。
3. **结构化审校协议**：把提议、反例、证据、异议、裁决和最终产物变成可追踪对象。
4. **权限与数据去向可见**：每次运行明确显示 Agent、Provider、网络去向、目录权限和可写范围。
5. **真实任务评测资产**：积累两院场景的脱敏任务集、质量量表、失败样本和适配兼容数据。

最容易被复制的是“支持九个 Agent”和“一个群聊窗口”；最难复制的是经过真实任务证明的协议、评测集、政策适配和用户信任。

### 4.4 成本定位

RoundRelay 不追求最低推理成本，而追求高价值任务的风险降低和整合时间缩短。默认仍应优先单 Agent，只有在以下条件满足时才建议升级为多 Agent：

- 任务失败代价高；
- 存在多个合理方案或明显盲区；
- 需要独立审查或反证；
- 用户愿意用更长等待换取更高置信度。

产品需要显示预计 Agent 数、轮数和可能耗时，避免“自动讨论”成为不可控的成本放大器。

### 4.5 Can't / Won't

竞争者“不会做”或“难以同时做好”的部分，才值得作为长期防御：

- 云端平台通常更适合集中管理，不一定愿意让本地 CLI、会话和目录成为一等公民。
- 单 Agent 厂商不会优先支持竞争 Agent 的平等协作和结果对照。
- 通用聊天工具不会深度承担 Agent 进程、权限、会话恢复和工作区副作用。
- RoundRelay 自己也明确不做云端多人通信、模型托管和无限自治，以换取本地可信和产品聚焦。

## 5. 产品原则

1. **结果先于对话。** 每次高价值任务都应有目标、产物、验收和未决问题，不能以消息数量衡量成功。
2. **单 Agent 默认，多 Agent 升级。** 简单任务不应强制组队；系统应解释什么时候值得增加 Agent。
3. **人类拥有目标、权限和最终裁决。** Agent 可以提议和质询，不能替用户承担责任。
4. **本地优先必须如实表达。** RoundRelay 不上传会话到自己的云端，不代表所选 Agent 或 Provider 不出网。
5. **权限必须可见、最小且可撤回。** 默认只读；写入必须显式、可追踪、可比较、可回滚。
6. **异构必须有实质意义。** 同一底层模型、同一提示词产生的多个角色不能被包装成“独立专家”。
7. **分歧比虚假共识更有价值。** 允许保留少数意见、证据不足和无法裁决，不以全员同意作为唯一成功条件。
8. **协议状态由程序管理。** 轮次、角色、预算、停止条件和失败处理应由确定性状态机控制，不能完全依赖提示词自报。
9. **可复现优先于炫技。** 记录 Agent/版本/模型/Provider/权限/上下文范围和产物，支持重跑与对照。
10. **保持单机架构简单。** 在证明需要前，不引入服务器、数据库集群、远程队列或微服务。

## 6. 目标产品模型

### 6.1 从“群聊”升级为“任务”

建议逐步引入以下本地对象，仍可保存在单机持久化层，不需要服务器：

| 对象 | 关键字段 | 作用 |
| --- | --- | --- |
| 任务 Task | 目标、背景、约束、验收、敏感级别、预算 | 防止对话偏离结果 |
| 参与者 Participant | Agent 类型、版本、模型/Provider、能力、角色 | 解释每个观点来自谁、能做什么 |
| 上下文包 Context Pack | 用户消息、选择文件、Skill、历史摘要、外发范围 | 让用户知道 Agent 实际收到什么 |
| 运行 Run | 协议、轮次、超时、调用序列、权限、状态 | 提供可停、可恢复、可审计的执行单元 |
| 论点 Claim | 结论、依据、提出者、置信度 | 支持质询和合并 |
| 异议 Objection | 针对论点、反例、严重度、状态 | 防止“大家都同意”掩盖未解决问题 |
| 证据 Evidence | 来源、片段、文件位置、验证状态 | 区分事实、推断和幻觉 |
| 产物 Artifact | 文档、代码 diff、清单、决策备忘录 | 把对话转为可继续工作的结果 |
| 裁决 Decision | 采用、拒绝、保留意见、责任人 | 明确人类最终责任 |

### 6.2 推荐的结构化质询协议

首个协议只做一个，不建设通用工作流编辑器。建议选择“方案红队”协议：

```text
用户定义任务与验收
        ↓
提议者生成初稿
        ↓
反方寻找关键反例和失败条件
        ↓
证据审查者核对引用、代码位置或数据口径
        ↓
整合者合并结论、保留未解决异议
        ↓
用户接受、要求重跑或终止
```

程序必须控制：角色分配、每步输入、最大轮数、每 Agent 超时、总预算、失败降级和停止条件。提示词负责内容生成，不负责决定系统是否“真的达成共识”。

### 6.3 停止条件

任一条件满足即可停止，不要求全员一致：

- 用户接受当前产物；
- 所有高严重度异议已解决或明确转为“需人工判断”；
- 新一轮没有新增有效论点或证据；
- 达到时间、轮数或调用预算；
- 关键 Agent 连续失败；
- 数据去向或权限条件发生变化，需要用户重新确认。

### 6.4 能力清单而非统一假设

每个 Agent 应有可机器读取的能力清单，至少包括：

- 操作系统与已验证版本；
- 是否支持原生会话恢复；
- 是否支持图片及数量限制；
- 是否支持本地 Skill 引用；
- 只读和写入模式的实际保障等级；
- 可使用的 Provider 与是否出网；
- 最大运行时长、取消可靠性和已知兼容问题。

混合群组发送图片、Skill 或写入请求前，系统应按目标 Agent 显示兼容结果。不能让不支持某能力的 Agent 静默失败，也不能把同一附件无差别传给所有 Agent。

## 8. 指标与评测

### 8.1 北极星指标

**每周被用户采纳的高价值任务数。**

“采纳”必须由用户明确标记为以下之一：直接使用、轻改使用、进入正式评审或产生被保留的工作区产物。只发送消息、完成一轮调用或模型自报共识都不算采纳。

### 8.2 当前阶段唯一关键指标

在第 12 周前，唯一关键指标是：

> **试点用户提交的目标任务中，被标记为“直接使用或轻改使用”的任务比例。方向性门槛为 60%。**

相对用户当前最佳单 Agent 的 20% 盲评质量或风险发现提升是配对实验的扩大决策门槛，不与采纳率拼成一个不可诊断的复合指标。两项当前基线均未知；小样本阶段只能作为方向性证据。

### 8.3 指标体系

| 类型 | 指标 | 试点目标 | 说明 |
| --- | --- | --- | --- |
| 激活 | 安装后 15 分钟内成功完成首个 Agent 回复 | >= 70% | 排除缺少 Agent/认证的非目标用户后计算 |
| 激活 | 7 天内完成首个多 Agent 目标任务 | >= 40% | 不是随意群聊 |
| 价值 | 直接使用或轻改使用率 | >= 60% | 用户任务级标记 |
| 价值 | 相对最佳单 Agent 的盲评提升 | >= 20% | 质量或风险发现至少一项 |
| 效率 | 从任务开始到可用结果的总人工时间 | 降低 >= 30% | 计入用户整合和返工，不只算模型延迟 |
| 质量 | 经人工验证的新增关键问题数 | 每个适用任务 >= 1 | 只算单 Agent 未发现且确实成立的问题 |
| 留存 | 目标用户第 4 周仍每周使用 | >= 35% | 样本量较小时同时报告人数 |
| 可靠性 | Agent 调用非用户原因失败率 | < 5% | 按 Agent/版本拆分 |
| 可靠性 | 停止命令在 5 秒内终止进程树 | >= 99% | 真机验证 |
| 安全 | 未授权工作区写入 | 0 | 一票否决 |
| 安全 | Provider/密钥/可执行路径泄露到渲染层或日志 | 0 | 一票否决 |
| 隐私 | 未告知的数据外发 | 0 | 一票否决 |
| 成本 | 每个被采纳任务的 Agent 调用数/耗时 | 持续下降 | 防止用无限轮数换质量 |

### 8.4 对照实验

每个优先场景先准备至少 10 个脱敏任务做方向性试点，采用配对交叉设计：

1. 为同一任务准备等价输入和统一交付要求，由同一用户分别使用当前最佳单 Agent 与 RoundRelay；顺序随机并做交叉平衡，避免学习效应固定偏向后一种工具。
2. 预先指定一个主要结果，例如总盲评分或关键风险发现率；其他维度作为次要结果，避免试验结束后挑最有利指标。
3. 至少两名领域评审独立盲评，使用固定 1-5 分量表评估正确性、完整性、关键风险、可执行性和证据质量，并记录拒用原因。
4. 报告配对差值、相对与绝对提升、样本量和 95% 置信区间；小样本可使用 bootstrap 区间，但不得仅凭点估计宣称“统计显著”。
5. 报告评审一致性：序数总分优先使用加权 Cohen's kappa，连续汇总分可使用 ICC；一致性不足时先校准量表，不进入扩大决策。
6. 同时记录总等待时间、用户操作时间、返工时间、调用次数和最终采纳。多 Agent 只有在质量收益覆盖时间与成本时才进入默认推荐。

每场景 10 个任务只用于发现方向、量表问题和明显失败，不足以单独证明普遍或显著优势。扩大试点前应根据观察方差补充配对样本，并报告不同用户和任务类型下是否方向一致。不要用“用户觉得很酷”“产生了更多观点”作为通过依据。

## 9. 架构、安全与隐私门槛

### 9.1 目标架构原则

继续保持单机 Electron 架构，但在代码职责上逐步形成五层：

```text
Vue 渲染层
  -> 窄 preload API
  -> Electron 主进程
       |- 策略与授权层：数据去向、目录权限、预算、用户确认
       |- 编排状态机：角色、轮次、停止、失败降级
       |- 上下文与产物层：消息、文件引用、Skill、结果、审计
       |- Agent 适配层：能力清单、参数、会话、取消、输出解析
       `- 本地持久化与安全存储
  -> 本机 Agent CLI / 用户批准的 Provider / 白名单安装源
```

近期不拆微服务。若 `LocalWorkspace` 同时承担持久化、提示构造、编排和运行状态的复杂度开始阻碍测试，再按上述边界拆分；不是为了“架构漂亮”提前重写。

### 9.2 隐私真相

产品必须在 UI 和文档中同时表达以下事实：

- 群组、消息和编排状态不上传到 RoundRelay 自有云端。
- Agent CLI 可能根据自身配置访问外部模型、更新服务或工具。
- 用户配置的 Provider 会收到被传入的提示、选中文件内容或工具结果。
- 本地 JSON 会话未做应用层加密，安全性依赖设备账号、磁盘加密和本地访问控制。
- Agent 进程拥有本地操作系统用户权限；RoundRelay 的只读参数不是完整 OS 沙箱。

任何“完全本地”“数据绝不出机”的宣传都必须经过运行模式限定。建议使用三种明确标签：

| 模式 | 条件 | 可用文案 |
| --- | --- | --- |
| 本地状态 | 会话和编排状态只保存在本机 | “RoundRelay 不上传会话状态” |
| 批准出网 | Agent 使用用户批准的外部 Provider | “内容将发送至：具体 Provider/地址” |
| 受控本地推理 | 所有目标 Agent 指向经批准的本地或内网模型，且网络检查通过 | “本次运行未配置公网模型出口” |

### 9.3 发布前安全门槛

| 门槛 | 要求 | 未通过时处理 |
| --- | --- | --- |
| IPC 与渲染层边界 | 新 API 采用固定方法、主帧校验、严格入参；不暴露路径、密钥和任意 shell | 不合入 |
| Agent 能力验证 | 每类 Agent 独立验证读取、写入、取消、会话、附件和错误输出 | 标记实验或禁用相关能力 |
| 写入可逆 | 写入前显示范围；运行后展示 diff/变化；高风险删除或覆盖需再次确认；有恢复方案 | 只读开放，写入关闭 |
| Provider 外发 | 运行前可见地址、模型、目标 Agent 和上下文类型；切换 Provider 要重新确认 | 禁止运行 |
| 安装供应链 | 固定版本，校验摘要/签名，下载大小和域名受限，安装日志脱敏 | 关闭一键安装，改为文档引导 |
| 数据生命周期 | 导出、删除、备份恢复、异常退出恢复有测试 | 限制为低敏试点 |
| 本地数据保护 | 明确设备磁盘加密基线；高敏场景决定是否需要应用层加密与自动锁定 | 不进入高敏场景 |
| 审计来源 | 本地记录 Agent、版本、模型、Provider、权限、协议、开始/结束/停止原因 | 不用于正式决策留痕 |
| 应用分发 | 内部认可的签名、完整性校验、回滚与版本标识 | 不扩大试点 |
| 隐私验证 | 空闲启动无意外连接；每种 Agent 模式建立预期出网清单 | 不宣称受控本地模式 |

### 9.4 高风险设计提醒

- **附件混合路由**：当前适配器仅 Codex、Hermes 和 OpenCode 支持图片，且数量上限不同。现有实现会在不等上下文时整轮拒绝；真机验证仍须确认上游版本不会静默忽略参数。
- **Skill 引用**：渲染层只应看到经清洗的标识和名称，主进程重新校验并解析；不能让前端提供任意本地路径。
- **提示词注入**：本地文件和 Skill 同样是不可信输入。系统提示、权限和停止条件不能由被读取内容覆盖。
- **共识伪装**：Agent 输出标记只能作为协议输入，不能直接等同事实正确或组织批准。
- **同源偏差**：多个 Agent 可能使用同一模型或 Provider。产品应显示实际多样性，避免虚假独立性。
- **本地状态损坏**：当前 JSON 适合 Alpha；长历史、异常退出、并发写入和迁移需要专门测试。只有出现真实性能或一致性瓶颈时才评估 SQLite。

## 10. 两院试点与内部 GTM

### 10.1 试点目标

内部 GTM 的目的不是获得下载量，而是回答三个问题：

1. 哪两类任务值得多 Agent？
2. RoundRelay 是否比用户自己切换多个 CLI 更省时间、更可靠？
3. 两院能否在不制造错误安全感的前提下接受它的数据与权限模型？

### 10.2 试点人群

建议招募 12-20 名设计伙伴，分三组：

| 组别 | 人数建议 | 条件 | 任务 |
| --- | --- | --- | --- |
| 工程组 | 5-8 | 每周使用本地代码 Agent | 代码/架构审查、故障假设 |
| 产品与研究运营组 | 4-6 | 经常写方案、PRD、评审材料 | 方案红队、需求澄清 |
| 研究组 | 3-6 | 有可脱敏研究设计或技术文档 | 方法审校、证据缺口 |

优先招募现有 CLI 用户，不从“不会安装或认证任何 Agent”的大众用户开始。前两周只使用公开或低敏脱敏任务，高敏任务必须等隐私门槛和院内政策确认。

### 10.3 六周试点节奏

| 周次 | 动作 | 输出 |
| --- | --- | --- |
| 第 0 周 | 访谈、现有流程观察、采集脱敏任务 | 问题证据、基线耗时、任务集 |
| 第 1 周 | 安装与首次任务陪跑 | 激活漏斗、兼容问题、认知误区 |
| 第 2 周 | 单聊与手动多 Agent 审校 | 失败日志、第一次采纳率 |
| 第 3-4 周 | 两个任务模板和对照实验 | 盲评、时间、成本、风险发现 |
| 第 5 周 | 结构化角色的低保真验证 | 是否需要更复杂编排 |
| 第 6 周 | 复盘与继续/收缩/停止决策 | 决策备忘录与下一阶段范围 |

### 10.4 渠道与运营

- 通过现有院内协作渠道招募和发布版本，不在 RoundRelay 内建设远程社交或通知系统。
- 每位试点用户有一个明确任务场景和一名产品联系人。
- 每周发布一页状态：任务数、采纳率、失败、隐私/权限事件、已知兼容问题、范围变更。
- 建立本地诊断包导出，默认脱敏，用户确认后才能分享给支持人员。
- 版本说明必须区分“已验证 Agent”“实验 Agent”“仅检测未验证 Agent”。

### 10.5 试点决策门

| 决策 | 条件 |
| --- | --- |
| 扩大试点 | 安全一票否决项为 0；目标任务采纳率点估计 >= 60%；至少一个场景相对单 Agent 的预设主要结果点估计提升 >= 20%；同时披露分子/分母、配对样本量、评审一致性和 95% 置信区间。小样本达标只允许有限扩样，不得宣称统计显著 |
| 保持小范围继续探索 | 用户价值有信号但效果不稳定；可明确归因于一个可修复瓶颈 |
| 收缩为统一 Agent 工作台 | 单聊有留存，但多 Agent 质量/效率没有优势 |
| 停止自治方向 | 多轮质量不升反降、成本/延迟明显失控，或用户始终偏好人工切换 |
| 停止试点 | 出现未授权写入、未告知外发、密钥泄露或无法恢复的数据损坏 |

## 11. 组织与资源

### 11.1 最小可行团队

| 角色 | 建议投入 | 责任 |
| --- | --- | --- |
| 产品负责人 | 0.5-1 人 | 用户研究、范围、试点、指标、决策日志 |
| Electron/桌面工程师 | 1 人 | IPC、安全存储、持久化、打包、系统集成 |
| Agent 集成/评测工程师 | 1 人 | CLI 适配、协议状态机、真机矩阵、评测集 |
| 前端/交互工程师 | 0.5-1 人 | 任务化 UI、结果/异议视图、可访问性 |
| 安全与 IT 评审 | 0.2-0.5 人 | 数据政策、供应链、签名分发、威胁评审 |
| 领域设计伙伴 | 每个场景 2-3 人 | 提供任务、盲评结果、解释错误成本 |

如果只有两名全职工程师，应先覆盖 macOS、Codex/Hermes/OpenCode 等少量高使用 Agent 和两个任务场景。不要同时承诺九类 Agent 真机支持、Windows、公证发布、复杂自治和高敏数据。

### 11.2 所有权

每个路线图项必须有一个 DRI。推荐所有权：

- PM：首要用户、任务集、指标、范围变更、试点决策。
- 桌面工程负责人：本地数据、IPC、权限、分发、异常恢复。
- Agent 工程负责人：能力清单、适配器、协议、评测、兼容降级。
- 安全评审人：外发口径、安装供应链、写入门槛、高敏数据准入。
- 场景负责人：确认输出是否真正可用，而不是只看模型自评。

### 11.3 工作节奏

- 每周一次兼容矩阵与安全问题评审。
- 每周一次试点数据复盘，先看任务结果，再看功能反馈。
- 每两周一次版本候选，未通过退出条件不扩大用户。
- 所有中途新增需求进入范围变更表，明确接受、延后或拒绝。
- 每四周复审战略假设，尤其是“多 Agent 是否有净收益”。

## 12. 风险与反例

| 风险/反例 | 为什么重要 | 早期信号 | 对策 |
| --- | --- | --- | --- |
| 多 Agent 放大同一个错误 | 多个角色可能共享模型、数据和偏差 | 答案措辞不同但事实错误一致 | 显示模型/Provider 同源性；引入证据审查；与单 Agent 基线对照 |
| 群聊比终端更慢 | 顺序调用延迟线性增加 | 用户等待后仍复制结果回原 CLI | 默认单 Agent；只在高价值任务推荐多 Agent；提供进度与预算 |
| 用户要的是产物，不是讨论 | 长对话难复用 | 用户频繁手工总结或复制到文档 | 把结论、异议、下一步和文件 diff 做成一等对象 |
| “本地”造成错误隐私预期 | Agent 仍可能把上下文发给外部 Provider | 用户无法说出数据去了哪里 | 运行前外发说明、Provider 标识、受控本地模式验证 |
| 上游 CLI 快速变化 | 参数、输出和认证随版本改变 | 升级后静默解析错误或只读失效 | 固定兼容版本、真机回归、能力降级、适配器契约测试 |
| 写入权限造成破坏 | CLI 以本机用户权限运行 | 只读模式仍有文件变化，或写入超出目录 | 默认只读、文件变化审计、禁用未验证写入、恢复与确认 |
| 自动共识不可信 | 模型可迎合提示或错误输出标记 | 快速全员同意但人类盲评低 | 共识不等于结束；使用异议/证据/人工裁决状态 |
| 一次性新鲜感 | 多 Agent 界面有吸引力但没有重复价值 | 首周高使用、第四周归零 | 只围绕重复任务优化；用周采纳任务数而非消息数 |
| 支持面过宽 | 九类 Agent、两系统、附件、Skill 同时推进 | 兼容问题占据大部分研发时间 | 根据真实使用率收缩支持矩阵；实验能力显式降级 |
| 本地 JSON 达到瓶颈 | 长历史、迁移和崩溃恢复未验证 | 启动变慢、文件膨胀、恢复失败 | 建性能阈值和迁移测试；达到门槛后再考虑 SQLite |
| 院内使用无法运维 | 无账号服务器也意味着远程诊断有限 | 每台机器问题无法复现 | 本地脱敏诊断包、版本/能力清单、可重放测试，不上传会话 |
| 远程多人诉求牵引产品漂移 | 两院协作天然会提出共享需求 | 团队开始建设账号、频道、通知 | 结果通过现有协作工具分享；是否做远程协作需独立战略评审 |

### 12.1 什么时候不该使用 RoundRelay

- 任务答案明确、失败成本低、最佳单 Agent 几分钟即可完成。
- 所有 Agent 实际指向同一模型，且没有独立证据或工具差异。
- 用户需要多人实时共编、审批和组织通知。
- 工作区包含不允许发送到当前 Provider 的敏感内容。
- 用户无法监督过程，却希望 Agent 直接执行不可逆操作。

把这些反例做进产品提示，比强行扩大使用率更能建立信任。

## 13. 预演失败（Pre-mortem）

假设 6 个月后 RoundRelay 试点失败，最可能出现以下情形：

| 失败情形 | 根因 | 预防动作 | 责任人 |
| --- | --- | --- | --- |
| 大家试了一次，没人每周回来 | 产品优化了群聊观感，没有嵌入真实重复任务 | 用 20 个真实任务先定义模板；周采纳任务数作为北极星 | PM |
| 多轮讨论很长，但结果不比单 Agent 好 | 角色只是提示词扮演，缺少独立信息和证据 | 建单 Agent 对照；没有净提升就停止复杂自治 | PM + 评测负责人 |
| 发生敏感内容意外出网 | 用户把“本地应用”理解为“模型不出网” | 运行前显示 Provider/地址/上下文；高敏模式只允许批准端点 | 安全负责人 |
| Agent 修改了不应修改的文件 | 过度依赖上游只读标志，缺少变化检测 | 未经真机验证的 Agent 禁止写入；运行后展示并可恢复 diff | 桌面负责人 |
| 上游升级后大量 Agent 失效 | 没有版本策略和兼容矩阵 | 固定已验证范围、自动契约测试、实验标识、快速禁用 | Agent 集成负责人 |
| 研发被 Windows、市场、同步和工作流编辑器拖散 | 路线图没有明确非目标和决策门 | 每次新增范围必须说明牺牲项；阶段 2 未达标不启动阶段 3/4 | 产品负责人 |
| 无法通过院内安全审查 | 供应链、数据生命周期、审计和签名后补 | 第 0 周引入安全评审；按发布门槛逐项收口 | 项目负责人 |

## 14. 版本退出标准

### 14.1 内部 Alpha 退出标准（进入 12-20 人试点）

- [ ] 目标 macOS 设备上至少 3 个高优先 Agent 完成检测、认证、调用、续聊、取消、只读及其声明的图片/Skill 能力真机验证。
- [ ] 未通过验证的 Agent/能力在 UI 中明确标为实验或默认隐藏。
- [ ] 运行前可见 Agent、Provider/出网、工作目录和读写权限。
- [ ] 手动多 Agent 与有界自动讨论均可中止，进程树在门槛内结束。
- [x] 图片与 Skill 已完成渲染层、窄 IPC、主进程校验、持久化/回收、目标路由和自动化测试闭环；真实 Agent 兼容性仍由前两项门槛控制。
- [x] 首次引导已完成检测门槛、键盘/返回关闭、滚动锁、双语和打包 UI 冒烟；真实首次成功率仍需试点数据验证。
- [ ] 工作区数据可导出、删除；异常退出恢复测试通过。
- [ ] 没有渲染层路径/密钥泄露，没有未授权写入。
- [ ] 内部分发包来源和版本可验证，安装回退方式已记录。
- [ ] 已完成 8-12 次访谈和 20 个脱敏基线任务。

### 14.2 封闭 Beta 退出标准（扩大院内使用）

- [ ] 目标任务“直接使用或轻改使用”率点估计 >= 60%，并报告分子/分母及 95% 置信区间。
- [ ] 至少一个场景相对最佳单 Agent 的预设主要结果点估计提升 >= 20%，配对样本、评审一致性和区间估计均已披露，且不同用户/任务子组没有明显反向信号。
- [ ] 第 4 周目标用户周留存 >= 35%，同时报告绝对人数。
- [ ] 非用户原因 Agent 调用失败率 < 5%，按 Agent/版本可追踪。
- [ ] 未告知外发、密钥泄露、未授权写入均为 0。
- [ ] 安装件版本与完整性可校验，干净设备安装验证通过。
- [ ] 关键运行来源和结果可本地导出，问题可由脱敏诊断包复现。
- [ ] 至少两个任务模板由对应领域负责人确认“比聊天记录更可用”。

### 14.3 1.0 退出标准（考虑更广分发）

- [ ] 连续两个版本周期达到 Beta 价值和安全门槛。
- [ ] macOS 正式签名、公证、升级和回滚完成；Windows 若宣称支持则有独立真机与 CI 证据。
- [ ] 数据分类、Provider 准入、日志/审计和本地数据保护通过院内评审。
- [ ] 上游 CLI 版本兼容政策、停用机制和维护责任明确。
- [ ] 结构化质询在至少一个场景证明净收益；否则 1.0 不包含自治卖点。
- [ ] 支持、故障响应、发布节奏和长期维护人员已确定。

## 附录 A：战略画布

| 要素 | RoundRelay 选择 |
| --- | --- |
| 愿景 | 让高价值知识工作在用户掌控数据与权限的前提下，获得多种 Agent 能力的独立审校与可执行接力 |
| 首要细分 | 已使用多个本地 Agent、处理非公开任务、需要对结果负责的两院知识工作者 |
| 成本定位 | 不追求最低调用成本，追求重要任务的风险降低和整合时间节省 |
| 价值主张 | 从手工切换与复制上下文，转为一个本地、可控、可追溯的任务工作台 |
| 关键取舍 | 当前 RoundRelay 不做云端群聊、远程参与者、无限自治、模型托管和泛化工作流平台；完整两院混合平台作为独立上层战略评审 |
| 北极星 | 每周被用户采纳的高价值任务数 |
| 增长方式 | 两院设计伙伴驱动，先深做两个任务场景，再扩 Agent 和用户 |
| 核心能力 | Electron 安全边界、Agent 适配、本地 Skill/附件上下文、结构化协议、评测、数据去向与权限治理 |
| 防御性 | 经验证的任务协议、脱敏评测集、兼容矩阵、政策适配和长期信任，而非 Agent 数量 |
